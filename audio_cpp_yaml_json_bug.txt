--------------------------------------------------------------------------------
1. TL;DR
--------------------------------------------------------------------------------
llama-packer emits each audio.cpp model's launch command as a shell HEREDOC
inside the `cmd:` string. That heredoc requires real newline characters. The
config writer (llama_packer/writer.py:write_yaml) uses PyYAML's default
yaml.dump(), which serializes the multi-line string as a SINGLE-QUOTED YAML
scalar. Single-quoted YAML scalars FOLD line breaks into spaces. The newlines
are therefore erased from the file. At runtime `sh -c` sees a single line,
treats the trailing `exec audiocpp_server ...` as `cat` operands (never
executes it), writes an EMPTY server.json, and the audio.cpp server is never
launched. The model shows up in llama-swap's /v1/models (the config parses
fine) but its health check fails and it can never serve.

Only the three audio.cpp (audio-cpp backend) models are affected. The two
whisper.cpp models are single-line commands and are fine.

--------------------------------------------------------------------------------
2. Symptom (what the operator sees)
--------------------------------------------------------------------------------
- The llama-swap web UI / `curl http://localhost:8123/v1/models` LISTS the
  models kokoro-82m, qwen3-asr-0.6b, qwen3-tts-0.6b (so it looks "fixed").
- But any attempt to actually load/use one fails: the model never becomes

- The two whisper.cpp models (whisper-large-v3-turbo, parakeet-tdt-0.6b-v3)

Why /v1/models is misleading: listing only requires the entry to parse as a
valid dict with cmd/name/etc. It does NOT prove the cmd launches a working
process. Do not treat "present in /v1/models" as "working".

5. ROOT CAUSE ANALYSIS (the full chain)
--------------------------------------------------------------------------------
Step 1 — the intended command is a multi-line shell heredoc.
  llama_packer/backends/audio_cpp.py:build_cmd (lines 120-129) builds the
  command in Python with real newlines:

      payload   = json.dumps(server, separators=(",", ":"))       # :120  one line
      payload   = payload.replace('"__AUDIOCPP_PORT__"', "${PORT}")# :121
      config_path = f"/tmp/audiocpp-{slug}-${{PORT}}.json"         # :123
      cmd = (                                                             # :124
          f"sh -c 'cat > {config_path} <<JSON\n"
          f"{payload}\n"
          f"JSON\n"
          f"exec {binary} --config {config_path}'"
      )

  The in-memory string IS correct and valid:
      sh -c 'cat > /tmp/audiocpp-...-${PORT}.json <<JSON
      {"host":"127.0.0.1","port":${PORT},"backend":"vulkan",...,"models":[...]}
      JSON
      exec /mnt/pool/data/tools/audiocpp/audiocpp_server --config /tmp/...json'

  A POSIX `<<JSON` heredoc reads its body from the LINES AFTER the command
  line, up to a line that is exactly `JSON`. The body (the JSON) and the
  following `exec` MUST be on their own lines. The newlines are load-bearing.

  Why a heredoc at all: audio.cpp's server is configured by a JSON file
  (`audiocpp_server --config server.json`), and the port is only known at
  launch time (llama-swap assigns ${PORT}). So the JSON cannot be written at
  pack time with a fixed port; it must embed ${PORT} and be materialized at
  runtime inside the single `cmd:` string that llama-swap later substitutes
  and runs via sh -c. The heredoc is the mechanism to "write file, then exec".

Step 2 — the writer flattens the newlines.
  llama_packer/writer.py:write_yaml (lines 2009-2013):

      import yaml                                   # :21  (PyYAML)
      ...
      def write_yaml(config, path):                 # :2009
          payload = config.plain() if isinstance(config, EmittedConfig) else config
          with open(path, "w") as f:
              yaml.dump(payload, f,
                        default_flow_style=False, sort_keys=False,
                        allow_unicode=True)         # :2013

  There is NO style override (no default_style, no str representer, no
  ruamel here — verified by grep). PyYAML's emitter chooses a SINGLE-QUOTED
  scalar for these cmd strings (they contain `: `, `{`, `[`, `"`, etc., which
  make plain style unsafe). Per the YAML spec, a single-quoted scalar FOLDS
  internal line breaks into single spaces. So the three load-bearing newlines
  become spaces:

      sh -c 'cat > /tmp/...json <<JSON {"host":...,"models":[...]} JSON exec
      /mnt/.../audiocpp_server --config /tmp/...json'

Step 3 — the shell misparses the flattened line.
  With everything on one line, `sh -c` sees the command `cat` with two
  redirections (`> file`, `<<JSON`) and the leftover words
  `{json}`, `JSON`, `exec`, `/path`, `--config`, `file` as OPERANDS (filenames)
  to cat. Consequences:
    - The heredoc body is the lines after the command line = NONE -> empty.
    - `cat` tries to open files literally named `{"host":...}`, `JSON`,
      `exec`, `/mnt/.../audiocpp_server`, `--config`, `/tmp/...json` -> all
      "No such file or directory" (stderr).
    - `> /tmp/...json` redirect created an EMPTY file.
    - `exec audiocpp_server ...` is an operand, NOT a command -> never runs.
  Net: server.json is empty, audiocpp_server is never started, /health fails.

Step 4 — why whisper.cpp is not affected.
  whisper_server.build_cmd emits a single-line command
  (`whisper-server --host ... --port ${PORT} --model ... --parallel 1`) with
  no embedded newlines. YAML folding of spaces is harmless there.

Step 5 — why the fix "adding the bin paths" made the models APPEAR.
  A prior (separate) issue was that audio-cpp/whisper binaries were unresolvable
  at pack time, so infer_backend() returned None and the models were DROPPED
  from config.yaml entirely. That was fixed (profiles.yaml now has
  audio_cpp.bin and whisper.bin). Once the backends became "available", the
  models were emitted — but with the broken heredoc cmd. So the models went
  from "absent" to "present-but-unlaunchable". The current bug is the launch
  command, not the discovery.

8. IMPORTANT — the DOCUMENTED example is ALSO wrong
--------------------------------------------------------------------------------
docs/backends/audio-cpp.md:69 shows the emitted cmd using a FOLDED block
scalar:

    cmd: >
      sh -c 'cat > /tmp/audiocpp-chatterbox-${PORT}.json <<JSON
      {"host":"127.0.0.1",...}
      JSON
      exec /opt/audiocpp_server --config /tmp/audiocpp-chatterbox-${PORT}.json'

A FOLDED block scalar (`>`) ALSO collapses the line breaks to spaces (that is
the definition of `>`). So copying the documented form verbatim would produce
the SAME broken one-line heredoc. To preserve the heredoc you would need a
LITERAL block scalar (`|`), not `>`. This is a documentation bug too, and it
explains how the design likely slipped through: the intent (multi-line
heredoc) was documented with the wrong YAML block style, and the actual writer
goes a step further and emits single-quoted (equally destructive).

Bottom line: a launch command that depends on newlines is fragile under this
writer. Either force literal-block (`|`) serialization for such values, or
remove the newline dependency from the command (recommended, see section 11).

--------------------------------------------------------------------------------
9. OVERALL GOAL of llama-packer with respect to audio.cpp
--------------------------------------------------------------------------------
llama-packer's job: scan model directories (per profiles.yaml `dirs:`), read
each model's `.md` sidecar, pick a backend, and emit a llama-swap
`config.yaml` where every model is an entry with a FIXED `cmd` that starts a
server on llama-swap's `${PORT}`. Core invariant (audio-cpp.md:5-9,
audio_cpp.py:6-9): "one entry = one process with a fixed command line."

For PROXIED engine backends (audio-cpp, whisper-server, sd-server) the engine
is not a plain `--port` CLI; it needs a config/args that include the port,
which is only known when llama-swap launches it. So the emitted `cmd` must:
  (a) materialize a per-port config file at runtime (audio.cpp: server.json),
      embedding ${PORT} as a placeholder llama-swap will substitute; then
  (b) exec the engine binary pointed at that file.
audio.cpp is the case in point: `audiocpp_server --config server.json`, with
server.json = {host, port:${PORT}, backend, device, threads,
models:[{id, family, path, task, mode, default_request_options}]}. The
heredoc exists solely to do (a)+(b) inside one string.

The goal is that after `llama-packer` runs and llama-swap loads the config,
each audio model can be loaded on demand, pass /health, and serve its
OpenAI-style endpoint (POST /v1/audio/speech for tts,
POST /v1/audio/transcriptions for asr) via llama-swap's proxy. The bug breaks
step (a)+(b) for every audio.cpp entry.

10. RECOMMENDED FIXES (pick one; all then require a regen + reload)
--------------------------------------------------------------------------------
All options end the same way:
    cd /mnt/pool/data/tools/llama
    /var/uv/env/bin14/bin/python -m llama_packer            # regenerates
    #   (defaults: --profiles profiles.yaml --output config.yaml; also rewrites
    #    sibling config.env)
  The running server has -watch-config and auto-reloads. THEN verify by
  actually loading a model (section 12), not by /v1/models.

OPTION A — newline-free command (RECOMMENDED, most robust).
  Change audio_cpp.py build_cmd to emit ONE line with no embedded newlines, so
  no YAML style can ever break it. The JSON payload has no single quotes, so
  shlex.quote wraps it safely; ${PORT} survives because llama-swap does its
  ${VAR} substitution on the raw string BEFORE sh runs:

      import shlex
      payload = json.dumps(server, separators=(",", ":"))
      payload = payload.replace(f'"{_PORT_SENTINEL}"', "${PORT}")
      cmd = (f"sh -c 'printf %s {shlex.quote(payload)} > {config_path} "
             f"&& exec {binary} --config {config_path}'")

  Pros: bulletproof under any serializer; localized to one function; the cmd
  is self-contained. Cons: slightly less "pretty" than a heredoc; only fixes
  audio-cpp (whisper is already fine).

OPTION B — force literal block scalars in the writer.
  Add a PyYAML str representer so any string containing a newline is emitted
  as a literal block scalar (`|`), preserving newlines:

      def _literal_str(dumper, data):
          if "\n" in data:
              return dumper.represent_scalar("tag:yaml.org,2002:str", data,
                                              style="|")
          return dumper.represent_scalar("tag:yaml.org,2002:str", data)
      yaml.add_representer(str, _literal_str)
      # then the existing yaml.dump(...) in write_yaml

  Pros: general (protects any future multi-line cmd); keeps the readable
  heredoc. Cons: relies on the representer being registered before dump; must
  be applied wherever write_yaml runs. (Alternative: switch write_yaml to the
  already-available ruamel.yaml and set a BlockScalar `|` style on cmd values;
  ruamel is already imported in model.py:1101.)

OPTION C — defense in depth: do BOTH A and B.

Also fix the doc: docs/backends/audio-cpp.md:69 `cmd: >` should be `cmd: |`
(or, if Option A is chosen, update the example to the newline-free form).
